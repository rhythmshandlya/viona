# Issues — 2026-03-17

## Issue 1: Agent doesn't understand "stacked layout"

**Status:** Open
**Severity:** Medium — limits creative direction quality

**Problem:**
The orchestrator/planner agent doesn't know what "stacked layout" means. When planning scenes, it should understand that stacked layout = animations on the top half, video on the bottom half. This is a core layout pattern for social ads (Meta, TikTok, Reels) where the speaker stays visible in one half while text/graphics overlay the other.

**Expected behavior:**
Agent should recognize "stacked layout" and plan scenes accordingly — splitting the frame into top (animations/text overlays) and bottom (original video footage), keeping the speaker visible.

**Root cause:**
The orchestrator system prompt `packages/sandbox/src/prompts/orchestrator-system.md` line 662-674 (LAYOUT SYSTEM section) explicitly says "There are no layout modes" and only describes raw coordinate placement. The Planner/Director skills mention "split-screen" in examples but never define "stacked layout" or other arrangement patterns as vocabulary. The Planner has no framework for deciding how to spatially arrange speaker footage vs animations.

**Status:** Fixed — added display mode vocabulary (stacked/overlay/fullscreen) to orchestrator prompt

**Fix location:** `packages/sandbox/src/prompts/orchestrator-system.md` — LAYOUT SYSTEM section (line 662+)

**Fix:** Added display modes section to orchestrator prompt with stacked (55% visual / 45% speaker), overlay (simple manifest items + complex Remotion scenes on transparent bg), and fullscreen (speaker hidden). Aligned with existing `STACKED_VISUAL_RATIO`, reviewer validation, and prompt-loader template vars.

## Issue 2: Thinking/reasoning shows as ugly chat bubble

**Status:** Open
**Severity:** Medium — poor UX during agent processing

**Problem:**
When the agent is reasoning or working before responding (e.g., "Planning your scenes now..."), the status text appears as a regular assistant chat bubble with a blinking cursor. This looks like a broken half-response rather than intentional processing state. The user sees a chat bubble with minimal text and a pulsing cursor, which feels wrong.

**Expected behavior:**
Agent thinking/reasoning should render as a distinct visual block — separate from chat bubbles. Examples:
- A collapsed "thinking" indicator (like Claude's thinking blocks) with a subtle animation
- An inline status bar showing what the agent is doing
- A muted, non-bubble element (e.g., italic text with a spinner, no bubble chrome)

The key distinction: chat bubbles are for conversational responses. Thinking/status messages are transient processing indicators and should look different.

**Root cause:**
The SSE stream sends `text` events for both conversational responses AND status messages (like "Planning your scenes now..."). The frontend treats all text the same — merges into ChatBubble with streaming cursor. There's no way to distinguish "agent is thinking and emitting a status line" from "agent is responding to the user."

**Possible approaches:**
1. **New SSE event type `thinking`** — backend emits `thinking` events instead of `text` for status lines. Frontend renders a `ThinkingIndicator` component instead of a ChatBubble. Requires orchestrator prompt changes to use a thinking tool/marker.
2. **Detect status patterns client-side** — heuristic: if the streaming message is short (< 50 chars), ends with "...", and is followed by a long pause, render as thinking. Fragile.
3. **Use the existing `progress` event** — the orchestrator already emits `report_progress` before dispatching subagents. The `ProgressIndicator` component already exists. The issue is that "Planning your scenes now..." is emitted as `text` BEFORE the progress event fires. Fix: remove the text status lines from the orchestrator prompt and rely solely on progress events for status indication.

**Recommended:** Option 3 — the progress system already exists. The orchestrator prompt tells the agent to "output ONE short sentence" before dispatch, which creates the ugly bubble. Remove that instruction and let `report_progress` + `ProgressIndicator` handle all status indication.

**Files involved:**
- `packages/sandbox/src/prompts/orchestrator-system.md` — STREAMING BEHAVIOR section tells agent to output status text
- `apps/web/src/features/editor-v2/components/ai-chat/ProgressIndicator.tsx` — already renders progress state
- `apps/web/src/features/editor-v2/components/ai-chat/ChatBubble.tsx` — currently renders all text the same

## Issue 3: Scene plan widget shows empty titles, NaN times, empty layouts

**Status:** Fixed
**Severity:** High — core feature broken visually

**Problem:**
The scene plan modal shows:
- Scene titles are empty (`<h3>` is blank, edit button says "Edit undefined with AI")
- Times show `NaN:NaN – NaN:NaN (NaNs)` — `startMs`/`endMs` are undefined
- Layout section shows the Move icon + "Layout" label but the value is empty
- Descriptions ARE populated correctly

**Root cause:**
The agent sends scene data in a different shape than what `ScenePlanCard` expects. The component expects `{ title, startMs, endMs, description, layout }` but the agent likely sends `{ name, frames: [start, end], description, displayMode }`.

**Fix:**
- Made all Scene interface fields optional
- Added `resolveTitle()` fallback: `title` → `name` → `sceneFile` → `'Untitled'`
- Added `resolveTimeRange()` fallback: `startMs/endMs` → `frames[]` (converted at 30fps) → null (hidden)
- Empty layout sections hidden when `formatLayout()` returns empty string
- All rendering locations (inline card, modal header, edit button title) use resolvers

**Files fixed:**
- `apps/web/src/features/editor-v2/components/agent-widgets/ScenePlanCard.tsx`
